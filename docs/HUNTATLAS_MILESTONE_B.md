# Hunt Atlas Milestone B — XP and prediction evidence

**Premium experimental build:** `huntatlas/hunt-atlas.user.js` v1.9.5 (2026-10-13). Synthetic tests and GitHub Actions only; deployed combat-server behavior still requires user-led checking. See [roadmap](HUNTATLAS_ROADMAP.md), [Milestone A protocol](HUNTATLAS_MILESTONE_A_PROTOCOL.md) and [combat source contract](COMBAT_MODEL_CONTRACT.md).

## What changed

1. **Independent XP streams, not combined income.** A native `morte` receipt now explicitly preserves missing `xpTreinador` and `xpPokemon` as `null`. Each wall-clock rate has its own number of known receipts. If one stream is absent during a sampling window, that stream's measured rate is unavailable instead of assuming zero or borrowing the other stream. Observed current trainer XP/h still outranks a model **only when every eligible kill has a trainer XP value**.
2. **Cold-start XP/h is deliberately *unboosted*.** Previously `combatProfile.trainerXpMult` and `pokemonXpMult` were aggregated from earlier kills and reused on other hunts; this could apply VIP, streams, events and a catch-up boost after they expired or across a threshold. In v1.9.5, cross-hunt modeled `trainerXpPerKill = xpDoNivel(level)` and `pokemonXpPerKill = xpDoNivel(level)`. They remain two named streams and are marked `unboosted-upstream-shared`. The game may award more or less due to bonuses or special mechanics; the estimate does not pretend otherwise. When native receipts exist, they are used separately.
3. **Bonus observation, not bonus-stack invention.** A small allowlist tracks explicit numeric/boolean XP bonus fields from `welcome`/`estado` including trainer/Pokémon XP boosts, VIP, guild/rank, streams, events and catch-up, when present. Known expiration-style numeric fields are retained as scope evidence, **not** applied as verified multipliers. Unknown object formats remain `unverified`. Changes invalidate incompatible profiles/calibration. Missing fields are not guessed. XP-per-kill ratio jumps are recorded as bounded *possible bonus/catch-up transitions*, not a claim that a specific shop effect fired.
4. **Actual lead context matters.** Measurement keys include lead instance, level, held item, Mega, TM/AoE, observable Speed IV, combat stats, supplied move definitions, hunt, catalog and bonus snapshot. New profiles cannot silently reuse earlier high-DPS samples under a different loadout or XP bonus environment. Existing partial spawn-coverage and AoE-cast safeguards remain.
5. **Out-of-sample calibration.** After sufficient early combat sampling, the current hunt can freeze an **unmeasured** raw personalized kill-time prediction. A later independent sustained observed wall-clock rate is compared with that earlier frozen forecast. Only then can a bounded per-hunt ratio enter the session-local calibration store. Ratios are scoped to the exact lead/bonus/tier/catalog context, limited to 12 hunts in each of at most 4 contexts, expire after 90 minutes, and are never persisted as a cross-account hidden global correction. No comparison → factor 1.
6. **Ranking and error disclosure.** Measured/complete-model/static-baseline predictions have distinct source and fallback reasons. A heuristic expected-value range is shown explicitly **not** as a statistical confidence interval. When point estimates differ by less than their uncertainty, observed rates outrank weaker models. A Top 5 model-only winner is labeled a **leading candidate (uncertain)** rather than a guaranteed best hunt. Diagnostic output can show scope and count of calibration cases, signed forecast error, range, model coverage and XP bonus provenance.
7. **Limited combat timing upgrade.** The raw personalized one-hit and multihit estimator can use an explicitly known Speed IV to apply the wiki's separate global attack floor `max(400,900−10*IV) ms`. It retains observed per-cast damage (which implicitly includes actual physical/special type/stats) and spawn-point weighting and does **not** double-count AoE hits. Pure, deterministic `xpCooldownFromPower` and `xpMoveCooldown` helpers reproduce the shared curve and the distinct species-Speed/IV discount. Known Mega/TM fixed cooldowns must not be overwritten. **Important:** these cooldown helpers are *not* a validated full move-readiness scheduler; the forecast's fallback reason states the live scheduler is unknown.

## Confidence contract

| Input | Presented as | Caveat |
| --- | --- | --- |
| At least 6 wild kills and 60 seconds, complete relevant event XP stream, within current eligible session | **Measured** trainer/Pokémon XP/h separately | Sustained wall-clock time, stale after 2 minutes without a kill; no independent CI |
| Full spawn coverage and sufficient combat events for same lead | **Personalized combat model** | Inferred cadence/movement/wave costs; can use bounded past out-of-sample calibration from the same scope |
| Incomplete HP/damage coverage, or no personal combat samples | **Unboosted static baseline** | Unknown targets never silently omitted; known immunity is blocking |
| Missing verified VIP/guild/stream/event/catch-up stack | **Unboosted modeled XP** | Does not borrow a historical bonus multiplier or claim exact current game income |
| Forecast range | **Heuristic** | ±12/28% for strong/weaker measurements, ±30–65% for models; explicitly not statistically calibrated |
| Named Pokémon move candidate with cooldown | **Catalog/index possible**, or **observed move** after actual battle event | Index is not authoritative equipped skill; shared curve may not match final live cooldown |

## Remaining HA-05/07/08 live-engine dependencies

The source mirror lacks the full current server scheduling implementation. Without authoritative field meanings, we cannot call specific boost-stack and expiration values verified, distinguish a complete catch-up crossing formula, know ready/unready moves at each attack, simulate off-field cooldown pause, or assert deterministic healing/death downtime. The earlier personalized estimator remains a **model**, not a validated full real-time battle simulator. In particular, `xpMoveCooldown` does not silently replace observed cadence; that would manufacture scheduler accuracy.

Validation against a real profile should compare long windows with and without boosts, repeat hunts after lead/IV/TM changes, record `farmingEvidence` fields (not socket payloads), check Outland tier context and inspect `snapshot().prediction` source/coverage/range/error. Never disclose auth tokens or raw player data. The `forecast-milestone-b.test.cjs` tests are synthetic deterministic regressions only.

## Performance and deployment

Uses the existing WebSocket observer, current render path and local session records. No new network requests or intervals. The calibration store is bounded and is cleared on reconnect/closed socket, and mature cases expire after 90 minutes. Premium installation is still **manual from this private repository**; the regular `pokeidle-addons` copy is unchanged.
